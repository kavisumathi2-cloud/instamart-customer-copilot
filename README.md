# Instamart Customer Intelligence & Support Copilot

## Overview

This project implements an end-to-end customer intelligence and support copilot using synthetic Instamart-style e-commerce data.

The project addresses four business problems:

- Cleaning and validating raw customer, product, and order data.
- Segmenting customers and predicting customer lapse.
- Classifying support tickets while protecting personal information and enforcing guardrails.
- Retrieving policy information and demonstrating a guarded refund-agent workflow.

The project is divided into four parts:

- **Part A — Data Foundation:** Data cleaning, SQLite database creation, validation, and SQL analytics.
- **Part B — Customer Intelligence:** RFM-based customer segmentation and customer lapse prediction.
- **Part C — Support Ticket Triage:** PII redaction, ticket classification, output validation, retry handling, and token-budget controls.
- **Part D — Policy RAG and Refund Agent:** Policy retrieval, evaluation, refund decision scenarios, checkpoints, and simulated refund actions.

**Important:** All data is synthetic and fictional. The supplied `mock_llm.py` provides offline simulated language-model responses. Refund actions are demonstrations only; no real money is transferred.

**Q6 window-function interpretation:** `RANK()`, `DENSE_RANK()`, and `ROW_NUMBER()` rank customers by completed spending within each city. `RANK()` gives tied values the same rank and skips subsequent rank positions; `DENSE_RANK()` gives tied values the same rank without gaps; `ROW_NUMBER()` assigns a unique sequential number, using `customer_id` as a secondary sort key. The query filters to `spending_rank = 1`, returning the highest-spending customer(s) in each city. The executed query returned six rows, one for each city.

**Actual tie evidence:** The completed-spending data contains seven tied customer groups across Bengaluru (2), Mumbai (2), and Pune (3). For example, Bengaluru customers C0692 and C0734 each spent INR 2,598. Both receive `RANK() = 99` and `DENSE_RANK() = 99`, while `ROW_NUMBER()` assigns 99 and 100. The next customer, C0746, receives `RANK() = 101` and `DENSE_RANK() = 100`. This demonstrates the rank gap created by `RANK()` and avoided by `DENSE_RANK()`.

### K-Means model selection and segment profiles

K-Means was evaluated for K=2 through K=8 using standardized recency, frequency, and monetary (RFM) features. The evaluation used `StandardScaler`, `random_state=42`, and `n_init=10`.

| K | Inertia | Silhouette score |
|---:|---:|---:|
| 2 | 1820.7 | 0.465 |
| 3 | 1268.2 | 0.445 |
| **4** | **743.0** | **0.525** |
| 5 | 617.5 | 0.478 |
| 6 | 503.2 | 0.483 |
| 7 | 408.5 | 0.416 |
| 8 | 366.2 | 0.412 |

Inertia always decreases as K increases because additional centroids reduce within-cluster distance, so inertia alone cannot determine the best K; it must be read together with silhouette score and business interpretability.

K=4 was selected because it achieved the highest silhouette score (0.525) among the tested values. The inertia reduction also becomes less pronounced after K=4, providing an additional elbow-based reason to prefer four clusters over larger values. This is a practical choice for this dataset, not a claim that four clusters are universally optimal.

The final model clustered 1,175 customers with completed-order history. The remaining 25 customers, who had no completed orders, were assigned to a separate `No Completed Orders` group and were not included in K-Means.

### Customer lapse prediction

The lapse prediction task uses a cutoff date of **2025-09-01**. Customers with at least one completed order before the cutoff are included in the prediction cohort. A customer is labelled as lapsed if they place no completed order during the September 2025 label window.

**Cohort and split**

| Item | Result |
|---|---:|
| Customers in lapse cohort | 1,156 |
| Not Lapsed | 713 |
| Lapsed | 443 |
| Training rows | 924 (80%) |
| Testing rows | 232 (20%) |
| Split strategy | Stratified, random_state=42 |

**Baseline**

The baseline predicts every test customer as Not Lapsed. It achieves 0.616 accuracy but 0.000 F1 for the Lapsed class, demonstrating why accuracy alone is insufficient for this imbalanced classification task.

**Model comparison**

| Metric | Logistic Regression | Random Forest |
|---|---:|---:|
| Best cross-validation F1 | 0.651 | **0.681** |
| Test accuracy | 0.728 | **0.737** |
| Lapsed precision | 0.64 | **0.66** |
| Lapsed recall | 0.65 | 0.65 |
| Lapsed F1 | 0.65 | **0.66** |

Random Forest was selected based on its higher cross-validation F1, not on test-set performance. Its best parameters were `max_depth=8` and `min_samples_leaf=10`. The final test-set Lapsed F1 was 0.655.

**Training-only preprocessing and leakage controls**

- The train/test split is stratified and uses `random_state=42`.
- Imputation, scaling and one-hot encoding are fitted within the training pipeline and cross-validation folds only.
- Grid search uses training data only; the test set is reserved for final evaluation.
- Oversampling is applied only to the training data. Test rows are not resampled.
- Prediction features use completed-order history strictly before 2025-09-01. September 2025 orders are used only to construct the target label.
- Segment IDs, segment names and the Premium flag are not included in the model's prediction features.

**Oversampling comparison**

| Model | Lapsed precision | Lapsed recall | Lapsed F1 |
|---|---:|---:|---:|
| Original Logistic Regression | 0.644 | 0.652 | 0.648 |
| Oversampled Logistic Regression | 0.589 | 0.854 | 0.697 |

Oversampling improves recall and F1 for the Lapsed class, but reduces precision. This trade-off means more actual lapsers are identified, at the cost of more false-positive retention targets.

**Feature importance and coefficient interpretation**

The Random Forest's five most important features were:

| Feature | Importance |
|---|---:|
| Frequency | 0.280 |
| Monetary | 0.271 |
| Recency | 0.115 |
| Average delivery minutes | 0.061 |
| Cancellation rate | 0.052 |

Business reading of the top features:

- **Frequency:** The negative Logistic Regression coefficient means customers who order more often have lower lapse odds. Frequency is also the most important Random Forest feature.
- **Recency:** The positive coefficient means a longer gap since the last order is associated with higher lapse odds.
- **Monetary:** Monetary value is highly important in the Random Forest. In Logistic Regression its coefficient is positive: after accounting for frequency, higher spend is associated with slightly higher lapse odds. Frequency and monetary are correlated, so this is a conditional association, not evidence that spending causes lapse.
- **Average delivery minutes:** In Logistic Regression the coefficient is small and positive (+0.08), so longer average delivery times are associated with slightly higher lapse odds. It ranks fourth in Random Forest importance.
- **Cancellation rate:** In Logistic Regression the coefficient is small and negative (−0.12), so a higher cancellation rate is associated with slightly lower lapse odds in this synthetic dataset. This is the opposite of what might be expected, and the effect is small compared with frequency (−1.70), so it should not be over-interpreted; it may reflect correlation with other features. It ranks fifth in Random Forest importance.

**Premium retention list limitation**

The Premium flag is assigned using the Top Value segment from whole-window RFM segmentation. It is applied after prediction to create an illustrative retention list; it is not a model feature. Because this flag uses information from the full observation window, the Premium-filtered retention list is **not a fully leakage-free evaluation**. In the current test set, 40 customers were Premium; the top-10 retention list contained 1 customer who actually lapsed. This list should be treated as a prioritisation example, not as an unbiased measure of model performance.

The saved model was reloaded and its predictions matched the original model's predictions exactly.

The ticket-triage pipeline redacts personally identifiable information before classification. Before each model call, explicit privacy assertions inspect both the system and user prompt messages and reject the call if any supported email-address, phone-number, or order-ID patterns remain. ### Classification and guardrails

The pipeline evaluates zero-shot and few-shot classification using the supplied offline mock language model. Invalid or empty responses are handled using validation, retry, fallback, or skip behaviour as appropriate.

Recorded classification results:

| Measure | Zero-shot | Few-shot |
|---|---:|---:|
| Total tickets | 164 | 164 |
| Tickets classified | 147 | 147 |
| Empty tickets skipped | 4 | 4 |
| Long tickets skipped | 4 | 4 |
| Classification accuracy | 85.7% | 100% |

The accuracy figures apply to the 147 classified tickets, not all 164 input tickets. The four empty and four long tickets were skipped and are not included in that accuracy denominator.

The four long tickets (T0161, T0162, T0163 and T0164) were each estimated at 734 tokens after PII redaction, for a combined estimated 2,936 tokens. Each exceeded the 400-token ticket limit and was routed to human review without being sent to the language model. These four tickets therefore used zero model tokens.


Few-shot classification achieved 100% accuracy compared with 85.7% for zero-shot classification across the 147 classified tickets. It consumed 22,660 tokens (154.15 per classified ticket), compared with 11,584 tokens (78.80 per ticket) for zero-shot, approximately 95.6% more tokens per ticket. The additional cost can be justified for ambiguous or high-impact tickets, such as fraud-related cases, when incorrect routing could delay critical support and the token budget allows it. Zero-shot is more economical for routine, lower-risk tickets or strict token budgets; a practical system can reserve few-shot prompting for uncertain or high-risk cases. The separate budget demonstration enforces a 6,000-token limit, classifying 76 tickets and marking 76 as budget-exhausted.

### Refund-agent policy and guardrails

The refund agent uses synthetic order information and retrieved policy information to decide whether to refund, deny, escalate, or stop safely.

Recorded policy thresholds:

- Late-delivery threshold: more than 45 minutes.
- Refund-request window: 7 days.
- Automatic refund limit: INR 1,000.
- Higher-value requests require human approval.
- Missing orders must not be refunded.
- The agent must stop safely when its limits are reached.

The agent exposes its tools through a TOOLS_SPEC list and a TOOL_MAP dictionary. get_order reads from data/instamart.db using a parameterized query. issue_refund and escalate_to_human append a timestamped record with the tool name to outputs/refund_ledger.jsonl.

All refunds are simulated. No real payment or transfer occurs.

## Limitations and Next Steps

- The dataset and policy documents are synthetic; the results do not represent real Instamart customers or official policies.
- The supplied language model is a deterministic offline mock, not a production language model.
- Classification and lapse-prediction metrics describe recorded evaluation runs and may change if data generation or training procedures change.
- Customer segmentation is descriptive and should not be interpreted as proof of customer intent.
- Lapse prediction depends on the observation window, label definition, feature availability, and leakage prevention.
- The retention list supports prioritisation but does not guarantee future customer behaviour.
- Refund actions are simulated and must not be connected to real payment systems without production-grade authentication, authorisation, audit, monitoring, and human-approval controls.
- The controlled crash-resume test covers interruption after a successfully saved checkpoint. A crash between a tool side effect and checkpoint persistence remains a possible duplicate-execution window; production use would require stronger transactional or idempotent side-effect handling.
- A production implementation would require stronger monitoring, security reviews, policy versioning, data governance, and evaluation on representative real-world data.
