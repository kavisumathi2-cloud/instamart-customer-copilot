# Instamart Customer Intelligence & Support Copilot

## Overview

This project implements an end-to-end customer intelligence and support copilot using synthetic Instamart-style e-commerce data.

The project addresses four business problems:

- Cleaning and validating raw customer, product, and order data.
- Segmenting customers and predicting customer lapse.
- Classifying support tickets while protecting personal information and enforcing guardrails.
- Retrieving policy information and demonstrating a guarded refund-agent workflow.

The project is divided into four parts:

- **Part A — Data Foundation:** Data cleaning, SQLite database creation, validation, and SQL analytics.
- **Part B — Customer Intelligence:** RFM-based customer segmentation and customer lapse prediction.
- **Part C — Support Ticket Triage:** PII redaction, ticket classification, output validation, retry handling, and token-budget controls.
- **Part D — Policy RAG and Refund Agent:** Policy retrieval, evaluation, refund decision scenarios, checkpoints, and simulated refund actions.

**Important:** All data is synthetic and fictional. The supplied `mock_llm.py` provides offline simulated language-model responses. Refund actions are demonstrations only; no real money is transferred.

### Technology stack

- Python 3.11+
- SQLite 3.25+
- pandas
- NumPy
- scikit-learn
- joblib
- pytest for automated tests

The supplied `generate_data.py` and `mock_llm.py` files must remain unmodified.

## Reproduce

Run the following commands from the repository root in Windows PowerShell. Execute the steps in order because later steps depend on files generated by earlier steps.

### 1. Create and activate a virtual environment

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

If PowerShell blocks environment activation, run:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
.\.venv\Scripts\Activate.ps1
```

```powershell
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 3. Generate synthetic data

```powershell
python generate_data.py
```

### 4. Inspect and clean the data

```powershell
python src/inspect_data.py
python src/clean_data.py
```

### 5. Build and validate the SQLite database

```powershell
python src/build_database.py

```

### 6. Run SQL analysis


The SQL queries are documented in `sql/queries.sql`.

### 7. Build customer features and segments



### 9. Run support ticket triage


```powershell

```

### Customer lapse prediction

The lapse pipeline creates a labelled cohort, prepares customer features, compares candidate models, evaluates the selected model, and saves the model and retention outputs.

Recorded selected-model results:

| Metric | Result |
|---|---:|
| Selected model | Random Forest |
| Test accuracy | 0.737 |
| Lapsed-class precision | 0.659 |
| Lapsed-class recall | 0.652 |
| Lapsed-class F1 | 0.655 |

The recorded model was selected using cross-validation F1. Preprocessing should be fitted on training data only, and future information must not be used to construct prediction features.

**Limitation:** A retention list is a prioritisation aid, not a guarantee that a customer will lapse. Features derived from a full observation window can introduce leakage if they are not restricted to information available at prediction time.

Recorded classification results:

### Refund-agent policy and guardrails

The refund agent uses synthetic order information and retrieved policy information to decide whether to refund, deny, escalate, or stop safely.

Recorded policy thresholds:

- Late-delivery threshold: more than 45 minutes.
- Refund-request window: 7 days.
- Automatic refund limit: INR 1,000.
- Higher-value requests require human approval.
- Missing orders must not be refunded.
- The agent must stop safely when its limits are reached.

All refunds are simulated. No real payment or transfer occurs.

## Limitations and Next Steps

- The dataset and policy documents are synthetic; the results do not represent real Instamart customers or official policies.
- The supplied language model is a deterministic offline mock, not a production language model.
- Classification and lapse-prediction metrics describe recorded evaluation runs and may change if data generation or training procedures change.
- Customer segmentation is descriptive and should not be interpreted as proof of customer intent.
- Lapse prediction depends on the observation window, label definition, feature availability, and leakage prevention.
- The retention list supports prioritisation but does not guarantee future customer behaviour.
- Refund actions are simulated and must not be connected to real payment systems without production-grade authentication, authorisation, audit, monitoring, and human-approval controls.
- Checkpoint files and run logs should be tested through a real simulated interruption and resume procedure before claiming that crash recovery has been fully demonstrated.
- A production implementation would require stronger monitoring, security reviews, policy versioning, data governance, and evaluation on representative real-world data.
